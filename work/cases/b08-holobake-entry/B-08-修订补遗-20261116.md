## 第一节｜K1-K5 依赖图修正（R1）

### 1.1 原始依赖声明（总控综合判断第四节）

原始输出称：
- K1 内部数据拉取（1-2 天）→ Holobake 内部，无外部接触
- K2 租金询价（2-3 天）→ 当地商铺中介
- K3 竞品盘点（2-3 天）→ 大众点评/美团 + 实地
- K4 渠道谈判（1-2 周）→ 渠道方合同条款
- K5 铺位查询（1 天）→ 中介 + 商圈物业

原始声称并行关系：K1/K2/K3 并行、K4 与 K2 同步、K5 先行。

原始工期汇总："3-5 周"——**与分项工期不一致**。

### 1.2 原始工期推导问题

独立复核（PR #57 + 01-B-08-v1.1独立复核.md B08-R2）指出：
- K1+K2+K3 串行相加是 5-8 天，而总控声称并行后应为并行组最大工期；
- K4 单独 7-14 天，才是关键路径；
- 原始"3-5 周"的总估算与分项 1-14 天的区间无法对齐；
- 若 K5 先行、K1/K2/K3 在 K5 后并行、K4 贯穿，必须给出明确的先后约束。

### 1.3 修正后的依赖图

按 PR #57 给出的正确依赖关系：

```
K5（铺位查询，1 天）
  └─→ K1（内部数据拉取，1-2 天）  ──┐
      → K2（租金询价，2-3 天）      ├─ 并行组（上限取 max）
      → K3（竞品盘点，2-3 天）     ─┘
      
K4（渠道谈判，7-14 天）── 独立贯穿，与 K2 部分重叠
```

关键路径公式（PR #57 确认）：

```
总工期 = max(K1 + K3, max(K1, K5) + K2, K4)
```

### 1.4 修正后的工期重算

使用总控原始声明的分项工期区间（下限/上限）：

| 取证项 | 原始工期 |
|--------|----------|
| K1 | 1–2 天 |
| K2 | 2–3 天 |
| K3 | 2–3 天 |
| K4 | 7–14 天（原始"1-2 周"） |
| K5 | 1 天 |

**无缓冲重算**：

| 路径 | 下限 | 上限 |
|------|------|------|
| K1 + K3 | 1+2 = **3** | 2+3 = **5** |
| max(K1, K5) + K2 | max(1,1)+2 = **3** | max(2,1)+3 = **5** |
| K4 | **7** | **14** |
| **max（关键路径）** | **7** | **14** |

独立复核引用的另一组工期数字（B08-R2 中 K1=2-3, K2=3-5, K3=3-7, K5=1-3）：

| 路径 | 下限 | 上限 |
|------|------|------|
| K1 + K3 | 2+3 = **5** | 3+7 = **10** |
| max(K1, K5) + K2 | max(2,1)+3 = **5** | max(3,3)+5 = **8** |
| K4（隐含工期，由总估算反推） | **6** | **10** |
| **max（关键路径）** | **6** | **10** |

**20% 示例缓冲**（独立复核给出）：6×1.2=7.2 天，10×1.2=12 天 → **7.2–12 天**

### 1.5 原始"3-5 周"估算的问题

原始"3-5 周（21-35 天）"的总估算**无法由分项工期推出**。最可能的原因是：
- 将各分项工期与"差旅准备""内部排期""协调等待"等未列入 K1-K5 的隐形成本一起估算；
- 或对"内部人力 2-3 人"的协作同步时间做了粗略加成；
- 但这些隐形成本未在总控输出中显式列出，导致可验证性为零。

**修正要求**：总工期不得超过关键路径上限（含缓冲），隐形成本单独列明并标注为估算。

## 第二节｜对外联系审批边界统一（R2）

### 2.1 原始审批边界的矛盾（总控综合判断第六节）

原始输出第 6.1 节审批门禁中，将"执行取证计划（内部数据拉取、实地调研）"标为"否"（不须用户批准），理由是"内部信息收集，不涉及外部承诺或资金支出"。

但 K1-K4 取证项中实际包含：
- K1：委托调研员或外包团队 → **对外合同/资金**
- K2：当地商铺中介询价 → **对外联系/可能的中介费**
- K3：行业协会/渠道联系 + 消费者访谈 → **对外联系/个人信息收集**
- K4：渠道方合同条款审核 + 谈判 → **对外联系/合同条款**

### 2.2 修正后的审批边界

**K1-K5 全部为拟议取证计划，不是已获授权的执行指令**。逐项审批门槛如下：

| 取证项 | 是否须用户批准 | 审批门槛 | 原始输出中标注 |
|--------|---------------|----------|---------------|
| K1 Holobake 现有门店单店模型 | **是** | 若委托外部调研员/外包团队 → 资金支出 + 合同；仅内部数据拉取（无外部人员）→ 可在内部完成，不须单独审批（但仍须知会） | ⚠️ 原始标"否"，未区分内部 vs 外部委托 |
| K2 目标城市核心商圈租金 | **是** | 当地商铺中介询价 → 对外联系；若需付费房源库 → 资金支出 | ⚠️ 原始未单列 |
| K3 目标城市竞品盘点 | **是** | 大众点评/美团搜索 → 无审批；实地走访 + 消费者访谈 → 对外联系 + 个人信息处理 | ⚠️ 原始未区分公开信息 vs 访谈 |
| K4 合作渠道数据保障 | **是** | 渠道方合同条款审核 + 谈判 → 对外联系 + 合同条款；谈判结果可能影响后续方案选择 | ⚠️ 原始未标为审批项 |
| K5 铺位到期释放信息 | **是** | 中介沟通 + 商圈物业查询 → 对外联系；若涉及物业内部信息交换 → 敏感信息外发 | ⚠️ 原始未标为审批项 |

### 2.3 修正后的总原则

- 任何实际执行（包括实地走访、中介询价、消费者访谈、渠道谈判）**均须先取得用户对应授权**；
- 仅可在不发生费用、不对外接触、不收集个人信息的**桌面准备范围**内自主开展（如公开信息检索、内部数据整理、取证方案细化）；
- K1-K5 的取证内容、预算、接触对象、信息收集范围和风险**须逐项用户批准后才能执行**；
- "取证计划"本身是分析输出，不是执行授权。
