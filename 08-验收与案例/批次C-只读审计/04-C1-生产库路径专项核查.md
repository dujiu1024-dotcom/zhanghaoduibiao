### 4.2 差异原因分层分析

#### 【已确认】WAL checkpoint 是 SHA/mtime 变化的直接机制

归档库配置 `journal_mode=WAL`（批次 A 已确认，SQLite-vec 需要 WAL 模式）。当以下任一条件触发时，SQLite 会执行 checkpoint（将 WAL 数据合并入主文件、更新 mtime、可能改变 SHA）：
- 某次写操作后 WAL 页数超过 `wal_autocheckpoint`（默认 1000 页 ≈ 4 MB）
- WAL 中存在未合并数据时，一个**新的读写连接**尝试 checkpoint（依赖 SQLite 版本和并发连接状态）
- 显式 `PRAGMA wal_checkpoint()` 被调用

**已验证的脚本测试**（用临时 WAL 库）：
- 有 WAL 数据时，**用读写模式打开 + `PRAGMA query_only=ON` + 关闭**，不会自动 checkpoint、不会改变主文件 SHA/mtime
- 显式关闭最后一个连接后，SQLite 的自动 checkpoint 阈值未被触发（测试库 WAL 数据量小）
- 但对于 3.8 GB 的大库，WAL 管理行为可能有差异——**本项目大库场景下的精确触发条件 NOT_VERIFIED**

#### 【推断未验证】触发 checkpoint 的可能来源

按时间线推断，触发 checkpoint 的操作发生在 **17:40:34 ~ 17:41:11** 之间：

| 候选来源 | 可能性 | 依据 | 反证 |
|---------|--------|------|------|
| 批次 C 采集的 Python 脚本未正确关闭连接（异常退出） | 中 | Python sqlite3 异常退出时 SQLite 会做恢复性 checkpoint | 03 采集 commit 成功、脚本正常结束无报错 |
| 批次 C 采集脚本内部调用了其他写操作（check_on_change.sh / kick_change_checks 等） | 中 | 若采集脚本复用 rag.py 入口（含 cmd_rebuild / cmd_ingest 的子函数），可能触发写入 | 03 报告明确声明"全程只读"，且采集方式是 `sqlite3.connect(str(p))` + `PRAGMA query_only=ON` |

### 5.2 DB_PATH.unlink() 行为分析【代码推断】

| 项目 | 结论 |
|------|------|
| **操作目标** | `04-知识底座/rag/kbase.db`（代码默认路径） |
| **对归档库的影响** | **无**。归档库路径是 `99-归档/.../配置层/kbase.db`，与 DB_PATH 完全不同 |
| **异常处理** | **无显式处理**。`Path.unlink()` 默认 `missing_ok=False`，若文件不存在会抛 `FileNotFoundError`。但前面有 `if DB_PATH.exists()` 守卫，正常流程不会走到 unlink 不存在文件——**除非 TOCTOU 竞态（exists 检查通过后文件被其他进程删除）**，此场景极罕见 |
| **无二次确认** | cmd_rebuild 没有 `input()` 二次确认、没有 `--yes` flag、没有 dry-run 模式。直接删直接建 |
| **删除 WAL/SHM** | 会同时删 `DB_PATH-wal` 和 `DB_PATH-shm`（SQLite 用连字符命名 WAL/SHM，归档目录备份库也用连字符，此处一致） |

### 5.3 connect() 在 unlink 之后的行为【代码推断】

| 项目 | 结论 |
|------|------|
| **DB_PATH 不存在时 connect() 会怎样** | `sqlite3.connect(DB_PATH)` **自动创建空 SQLite 文件**（0 字节 header + SQLite 魔术字） |
| **随后的 SCHEMA 执行** | 空库上执行 SCHEMA → 创建 docs/segments/terms 等表 |
| **ingest_docs() 行为** | 从 `all_sources()` 扫描全部知识源，计算嵌入、写入向量、切段、入库 |
| **潜在风险** | 若 embedder 未就绪（check_embedder() 通过但 Ollama 服务异常），会在 ingest 中途失败，留下**部分重建的半成品库**（部分 docs 有向量、部分没有） |

### 5.4 对当前环境的实际影响

| 场景 | 结果 |
|------|------|
| 跑 `python rag.py rebuild` | DB_PATH = `04-知识底座/rag/kbase.db` **当前不存在** → `if DB_PATH.exists()` 为 False → 跳过 unlink → connect() 自动在该路径创建新库 → ingest 全量 → 新建一个**独立的空库副本**。**归档库完全不受影响** |
| 跑 `python rag.py init` | 同上，在 `04-知识底座/rag/` 下建一个**空表但有 schema 的库**，归档库不受影响 |
| 跑 `python rag.py ingest` | 同上，在 `04-知识底座/rag/` 下 ingest 全量，归档库不受影响 |

**结论**：在当前环境（DB_PATH 指向不存在的路径）下，`cmd_rebuild()` **不会删到任何有效数据**（因为目标路径本身是空的），反而会在错误位置创建新库。这反而构成了新的风险——误操作会在 `04-知识底座/rag/` 下生成一个假库，可能在后续评测或脚本调用中被错误使用。

### 5.5 unlink() 异常处理的完整分析【代码推断】

```
DB_PATH.exists()       → True  → DB_PATH.unlink()
                              → False → 跳过 unlink

DB_PATH.unlink():
  - 文件存在 → 删除文件，返回 None
  - 文件不存在 → 抛 FileNotFoundError（被 if 守卫阻止到达）
  - 无权限 → 抛 PermissionError（未捕获，直接崩溃）
  - 文件是目录 → 抛 IsADirectoryError（未捕获，直接崩溃）
  - 被其他进程锁定 → macOS 上可能成功删除（Python unlink 语义是解除目录项，文件句柄仍有效），也可能触发异常——NOT_VERIFIED
```

**异常处理缺口**：cmd_rebuild 没有 try/except 包裹 unlink 或 connect 调用。如果 unlink 抛异常，函数直接崩溃，**不会创建新库，但原库已经被删掉**——这是最坏情况（文件系统级不可恢复）。

## 6. 自动建库风险评估（保留原报告结论，补充归档库不受影响的澄清）

### 6.1 风险来源一：rag.py connect() 默认参数

```python
# rag.py 第 189-192 行
def connect(path: Path = DB_PATH, create: bool = True) -> sqlite3.Connection:
    if not create and not path.exists():
        sys.exit(f"数据库不存在：{path}，先跑 `python rag.py rebuild`")
    conn = sqlite3.connect(path)   # ← 关键：SQLite 标准行为，路径不存在则自动创建空文件
```

**风险逻辑**【代码推断】：
1. `sqlite3.connect(path)` 对不存在路径会**自动创建空 SQLite 文件**
2. `create=True` 分支的 `if create:` 只是额外执行 SCHEMA 和迁移，**不拦截 sqlite3.connect() 自身的自动建库**
3. 只有 `create=False` 时，`if not create and not path.exists()` 才会触发 `sys.exit`

**注意**：当前 DB_PATH 指向的路径（`04-知识底座/rag/kbase.db`）不存在。任何走 `create=True` 的命令（init/ingest/rebuild）都会**在那个位置创建新库**，不会碰归档库。

### 6.2 风险来源二：三个默认路径命令

| 命令 | 函数 | 建库条件 | 风险等级 | 对归档库影响 |
|------|------|---------|---------|-------------|
| `python rag.py init` | `cmd_init` → `connect()` | DB_PATH 不存在 → sqlite3.connect 自动建空库 → 执行 SCHEMA | **高**。在错误位置建空库，与归档库无关 | 无 |
| `python rag.py ingest` | `cmd_ingest` → `connect()` | 同上 | **高**。在错误位置 ingest 全量，归档库不受影响 | 无 |
| `python rag.py rebuild` | `cmd_rebuild` → 先 unlink 再 connect | DB_PATH 不存在 → 跳过 unlink → connect 在错误位置建新库 | **中**（archive 安全）但**误导性高**。用户以为在 rebuild 生产库，实际是在空位置新建 | 无 |

### 6.3 风险来源三：work/three_sources.py 无保护


### 6.4 风险不会触发的场景

- 所有 `create=False` 调用：路径不存在时 sys.exit 退出
- 所有 `mode=ro` URI 连接：路径不存在直接报错
- `build_index.py`：不使用 SQLite
