### 2.3 分层治理规则核验

V2 README 已规定：A 为通用默认层；B 必须匹配行业、地域、时间和来源有效期；C 按专业显式调用；D 必须匹配 project_id/customer_id 与权限；E 默认关闭并按明确授权检索。切段需继承来源、定位、授权、质量、有效期和敏感级别；D/E 敏感信息不得进入共享向量索引。

这些规则构成可审计的设计基线，但不能证明 Trae 当前运行时已按层过滤。D/E 当前没有可供核验的独立访问控制配置，列为权限隔离阻塞项。

## 4. 元数据与生命周期风险

V2 元数据规范要求稳定 knowledge_id、layer/domain/subdomain、知识类型、来源类型/名称/URI/locator、采集与更新时间、授权状态与证据、引用策略、质量/置信度/核验状态、适用范围、有效期、敏感级别、owner、生命周期状态、SHA256 和关联 ID。

重点发现：

1. 元数据规范已定义，但本轮无法读取本机 `metadata.csv`，无法验证 776 条记录的必填字段覆盖率。
2. 批次 A 记录 `docs=807` 与 `metadata.csv=776` 相差 31 条；报告将其归因于目录扫描入库。仅依赖 metadata.csv 无法完整重建数据库。
3. 批次 A 将 metadata schema version 和 chunking strategy version 记录为 null / `NO_VERSION_DECLARED`。后续需用明确版本号或不可变指纹管理。
4. `verification_status`（内容核验）与 `status`（生命周期）必须分离；active 不代表 verified。
5. 授权未知、来源未知、敏感级别不明的内容不得直接标记 active 或进入共享层。
6. 过期规则、冲突文档、二手材料和未经核验经验需单独标记，不得以“目录归类完成”视为内容已验证。

## 5. RAG 检索链路静态审计

仓库文档和 `04-知识底座/rag/rag.py` 描述的链路包括：

1. 输入查询；
2. 中文二元字组倒排召回；
3. 人工概念标签/同义词辅助；
4. bge-m3 本地向量召回；
5. 候选融合与阈值过滤；
6. 按质量档筛选并输出路径、段号/法条号和质量档；
7. 无答案时返回拒答/诊断，而不是强行输出段落；
8. 图谱查询作为辅助能力。

批次 A 记录数据库表包括 docs、segments、terms、segment_tags、seg_vec、graph_nodes、graph_edges。文档说明标签命中只代表主题关联，不是原文证据；重要引用必须回到原文核验。仓库没有实现独立 rerank 模块的证据，批次 A 亦记录“重排模型 N/A（仓库无重排）”。

参数基线以批次 A 的代码 SHA 和逐项核验记录为准，不沿用旧 README 的混合口径。当前代码基线记录 `SIM_FLOOR=0.66`；`ANSWER_MIN_COVERAGE` 受运行分支/环境变量影响；Top-K 按入口分别为 5/10/50。旧 README 与历史评测文档的参数/成绩存在差异，必须绑定 commit、代码哈希、数据库快照、题集哈希和运行环境后重新评测。

## 7. 重复、过期、冲突和来源缺失

本轮不能读取知识正文和 metadata.csv，故**不对实际重复率、过期率、冲突率、缺来源率作数量结论**。目前可确认的风险线索：

- 旧知识与 catalog/experience/图谱可能存在重复表达或跨目录重复登记，需基于文件 SHA、标题规范化和内容相似度抽样。
- 旧平台规则和法规存在版本/有效期问题；必须核对官方来源、生效/废止日期。
- 同一参数在 README、代码、历史评测报告之间出现不同口径，证明文档层存在版本漂移风险。
- metadata schema 与切段策略无显式版本，影响历史复现。
- 数据库 docs 与 metadata 条数不一致，需建立“目录扫描来源”与“metadata 登记来源”的来源追踪。

以上为风险项，不是已经证实的正文缺陷计数。
