## 一、审计结论

**结论：有条件继承，禁止整体平移。**

仓库已经积累了可复用的研究、证据管理、战略拆解、决策留痕、执行复盘、知识检索和风险治理资产。但当前系统的中心对象仍是「个人 FDE / 抖音 IP 账号」，不是一个可跨企业、行业和商业模式工作的操盘手。

应将现有资产拆成四层：
1. **通用操盘能力**：战略分析、市场研究、竞争分析、商业模式、营销与销售、经营分析、财务测算、组织与产能、风险治理、决策与复盘。

3. **场景模块**：个人 IP、抖音运营、内容生产、平台规则、账号增长、闲鱼试单等。
4. **个人偏好与历史事实**：个人身份表达、个人案例、个人服务边界、定价偏好、用户拍板记录。不得默认推广为所有客户的通用规则。

当前最重要的不是增加知识数量，而是解除个人账号业务对系统宪法的绑定、明确通用能力边界，并修复知识检索验收口径。

## 四、关键发现

### 4.1 系统宪法被个人 IP 目标锁定

`AGENTS.md` 第一条将「突出我这个人」设为唯一不可调的宪法级原则，并明确数据不能改变人设。这适合个人 IP 内容运营，却与通用商业操盘手的职责冲突：通用操盘手必须根据业务目标、客户价值、竞争事实和经营约束作判断，不能把某个操作者的人设设为所有决策的最高标准。

**处理：从通用宪法中移除；作为「个人 IP/创始人品牌」场景规则保留。**

### 4.2 证据纪律值得保留，但 A 库前置门禁过度刚性

现有规则要求所有判断先查 A 库，查不到就不得判断；并要求道的每格都必须挂 A 库依据。其价值是防止臆断，但通用商业决策经常面对新市场、新产品、未知竞争者或数据不足场景，不能因为知识库没有材料就停止分析。

**处理：继承证据分级、出处追溯和「库内无依据」标注；把 A 库从唯一前置门禁改成证据来源之一。允许基于外部调研、用户数据、业务数据、专家访谈和明确假设开展分析。**

### 4.3 道法术器有用，但不应成为所有任务的固定串行流水线

现有定义是方向与边界→路径全集→落地动作→工具与库，适合战略规划型任务；但日常经营分析、竞品快查、财务核算、紧急风险处置不一定需要完整经过四层。

**处理：保留为战略设计方法；对其他任务采用按需流程，不设置全局阻断。**

### 4.4 三轮自驳应分级触发

三轮整体挑战和审查闸能提高重大判断质量，但对所有小任务强制执行会增加时延和 token 消耗，也会让 Agent 把简单任务复杂化。

**处理：高影响/高风险/不可逆决策强制执行；一般分析至少做一次反证检查；事实提取和格式转换不执行完整三轮。**

### 4.5 七张 SOP 表是执行机制，不是通用商业方法论

`log_task.py`、`sop_tables.json` 和控制计划表形成了可运行的个人项目作业系统。但七张表中的字段、状态、前置条件和内容发布流程高度贴合原业务。

**处理：保留任务状态机、依赖检查、停滞告警、日志和验收机制；表结构按任务类型/项目模板加载，不把原七张表强加给所有商业任务。**

### 4.6 知识库的规模不能等同于知识能力

目录有 77 个细类、知识分类、经验库、图谱、RAG 和验收工具。但现有分类的核心仍是人性、传播、内容、用户市场、客户转化、平台增长、商业经营、风险治理和专业本体；战略、竞争、营销、财务、组织等企业经营能力的覆盖深度并不均衡。

尤其要区分：
- 有书目/有标题；
- 有二手笔记；
- 有可检索正文；
- 有可引用的一手来源；
- 有经过问题集验收、能够稳定召回的证据。

这五种状态不能合并成「已覆盖」。

### 4.7 RAG 目前不能作为通用决策的可信底座

当前面向 240 题的验收口径：235 道计分题，Recall@5 为 56.2%，候选上界 68.1%，排序损失 11.9 个百分点；60 条负集现场跑 44 条仍返回答案，硬答率 73.3%。这意味着检索召回和无答案拒答都存在明显问题。

此外，仓库里存在多个不同批次的检索报告：
- `04-知识底座/验收/报告-20261115-1651.md` 是 60 题骨架基线，Recall@5 为 45.5%，且各组只有 5 题。
- `04-知识底座/rag/eval/report.md` 是 20+12 小样本实验，记录 15/20 命中、5/12 硬答等数据。
- `04-知识底座/rag/README.md` 中另有 18/20、2/12 的旧口径表述。
- `05-给你看/06-这套库怎么用.md` 与 `05-给你看/01-现在到哪了.md` 已引用 240 题的较新口径。

这些报告不是同一评测集，不能横向拼接；README 与旧 eval 报告需要显式标注历史版本，避免误读。最终验收以固定 240 题、60 条负集、同一代码指纹的最新可复现实验为准。

### 4.8 Trae 加载边界需要按官方规则设计

官方 Trae 规则文档明确：
- 项目规则目录为项目内 `.trae/rules/`；
- 根目录 `AGENTS.md` 作为项目规则，需要在设置中开启「将 AGENTS.md 包含在上下文中」；
- 项目规则仅在可信工作区中加载；
- `.trae/rules/` 支持多层目录，但最多 3 层嵌套；
- 普通 Markdown 目录并不会因为存在于仓库就自动成为规则。

因此，`00–07` 的知识/设计文档应作为普通资料资产；只把少量高优先级行为约束写入 Trae Rules/AGENTS，具体方法通过可调用的技能、命令或任务入口组织。不能把整库内容复制进始终加载的规则。

官方依据： https://docs.trae.cn/ide_rules
https://docs.trae.cn/ide_get-started-with-trae

## 五、根因判断

当前系统的主要问题不是缺少一套更复杂的 Agent 架构，而是**通用操盘目标与原账号运营规则之间存在目标函数冲突**。

如果直接继承：
- Agent 会优先维护个人表达，而非最大化业务决策质量；
- A 库门禁会让未知问题无法推进；
- 道法术器和 SOP 表会把不同任务强制串行化；
- 内容运营知识会被误认为通用营销能力；
- RAG 命中结果会被误认为可靠事实。

因此，先做规则分层、资产隔离、知识缺口标注和检索验收治理，再进入架构落地。

## 九、用户拍板后的审计结论（2026-11-15）

用户已明确确认以下四项产品原则，作为后续设计的正式输入：

1. **通用商业操盘手与个人 IP 解耦**：通用系统以商业目标、客户价值、竞争事实和经营结果为判断依据；个人 IP 是独立场景包，不是通用宪法的最高目标。首个应用场景可以是个人 IP，但通用能力必须能在无个人资料条件下分析企业、产品、项目和其他个人业务。
2. **允许多源外部取证**：知识库不是唯一事实源。证据路径包括内部知识、外部公开资料、业务数据、用户/专家访谈、实验结果和明确标注的假设；重要结论记录来源、时间、可信度和适用边界。资料不足时应继续研究或提出验证方案，不得编造。
3. **监督式自主**：Agent 可自主理解任务、研究、分析、推演、提出方案、制定执行计划并在授权范围内推进；重大决策、资金支出、对外发布、合同承诺、不可逆操作及高风险动作必须先经人工审批。执行后需留痕和复盘。
4. **系统化建设知识体系**：采用 systematic 策略，先建立完整的通用商业能力地图与知识覆盖矩阵，再分域建设和验收；不能只靠遇到问题临时补知识。知识建设仍需区分书目、摘要、正文、可引用来源、经验样本和通过评测的可检索证据，不以资料数量代替能力验收。

以上是已确认的设计原则，不代表相应系统能力已经实现或验收通过。阶段 1 的最终验收仍待审查；在验收通过前不得启动阶段 2 实施。
