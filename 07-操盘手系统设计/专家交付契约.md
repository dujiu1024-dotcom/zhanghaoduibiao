# 专家交付契约

## 1. 通用派单格式

每个专家任务必须包含：
- task_id：全局唯一任务编号；
- parent_task_id：上级任务编号；
- assignee：专家角色；
- objective：需要回答的明确问题；
- scope：研究/分析范围与排除项；
- context_files：必须读取的文件路径；
- evidence_scope：可用来源和时间范围；
- constraints：预算、时间、数据权限、保密要求；
- risk_level：L0-L3；
- expected_output：交付文件与必填章节；
- due_condition：何时视为完成；
- dependencies：依赖任务和状态。

不完整派单不得假装已充分理解；专家应报告缺失字段及其影响。

## 2. 通用交付文件结构

文件名：`<task_id>-<role>-<slug>.md`

必须包含：
1. 任务编号、角色、版本、状态、更新时间；
2. 执行摘要；
3. 问题理解与范围；
4. 关键结论；
5. 事实与证据（证据 ID、来源、定位、日期）；
6. 推断及推理链；
7. 假设与验证方式；
8. 未知与信息缺口；
9. 分析过程/模型及适用边界；
10. 风险、反证和替代解释；
11. 建议与行动；
12. 对其他专家的依赖/问题；
13. 自检结果。

## 3. 结构化结论记录

每条结论建议使用以下字段：

| 字段 | 说明 |
|---|---|
| claim_id | 结论唯一编号 |
| statement | 一句话主张 |
| type | fact / inference / assumption / unknown / preference / recommendation |
| evidence_ids | 支撑证据 ID |
| reasoning | 推理链简述 |
| confidence | high / medium / low，并解释 |
| scope | 适用对象、地域、时间、场景 |
| counterevidence | 反向证据或替代解释 |
| falsifier | 什么证据会推翻 |
| owner | 负责专家 |

## 4. 证据记录契约

每条证据：
- evidence_id；
- claim_supported；
- source_name；
- source_type（官方/一手/二手/内部数据/访谈/实验等）；
- source_uri_or_path；
- locator（页码、段落、表格、时间戳）；
- published_at；
- collected_at；
- scope；
- reliability_note；
- rights_or_access；
- freshness_or_expiry；
- verification_status。

来源没有日期或定位时明确写 unknown，不得推测补齐。

## 5. 专家完成状态

- `draft`：尚未完成自检；
- `ready_for_review`：字段完整，等待总控审查；
- `blocked`：缺关键输入或权限；
- `rejected`：交付不符合契约；
- `superseded`：被新版本替代；
- `accepted`：总控审查通过并正式接收（仅总控可设置）。

专家不得自行将产出标记为 `accepted`；只有总控完成质量审查、证据核对和依赖检查后，才能将 `ready_for_review` 更新为 `accepted`。被拒绝的产出应标记 `rejected` 并记录整改要求。专家不能自行把自身产出标记为最终决策。

## 6. 质量门槛

- 关键事实必须有来源或标记未知。
- 事实、推断、假设、偏好、建议不得混写。
- 结论须说明适用范围和失效条件。
- 数据必须说明单位、时间、口径和计算方式。
- 不能完成时报告阻塞原因、已完成部分和最小解阻动作。
- 不允许只交模型名称或泛化建议。
- 不得代替总控做最终综合或执行授权动作。

## 7. 交接规则

专家只能引用已存在的 evidence_id、claim_id 和文件路径。引用缺失时先报告，不虚构 ID。跨专家依赖通过黑板中的问题/请求条目建立，不通过口头假设传递。
